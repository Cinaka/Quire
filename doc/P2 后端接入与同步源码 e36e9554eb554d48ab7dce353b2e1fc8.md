2. 任何时候，**`dirty = 1` 的本地记录不允许被服务端数据覆盖**（服务端版本只写进冲突缓冲，不落 `entries`）。

## 一、七条定案速查表

| # | 主题 | 定案 |
| --- | --- | --- |
| 1 | 注册登录与 JWT | **邮箱 + 密码**，P2 **不做验证码**（手机号与短信验证码整条推 P3）。`access` 15 分钟存 `localStorage.quire_access_token`；`refresh` 7 天存 **httpOnly Cookie**（同源反代，`Path=/api/v1/auth`）。游客数据靠 `meta.ownerUserId` 认领：空则**全量置 `dirty=1` 上行**；不为空且与登录用户不同则**拒绝混库** |

## 二、① 注册登录与 JWT

### 1. 邮箱还是手机号：P2 只做邮箱

手机号的成本不在代码，在**短信通道**：实名资质、模板报备、单条计费、以及为了防刷必须先有 Redis 的限流与验证码存储。这三样都不是 P2 的目标（P2 的目标是「本地数据能上云、多设备能对齐」）。

所以 P2 的账号形态是**邮箱 + 密码，无验证码**：

- `users.email` + `users.password_hash` 生效，`users.phone` 建了表但继续留空（表结构已在 P0 建好，无迁移）
- **不做邮箱验证链接**。P2 是单人自用阶段，未验证邮箱不影响任何功能；验证邮件与找回密码一并推 P3
- 密码规则只有一条硬限制：**长度 ≥ 8**。不做复杂度正则（会逼出「Aa1!」这类更弱的密码）
- 哈希用 `passlib[bcrypt]`（P0 已装），`bcrypt` 默认轮数，**绝不存明文**

<aside>
⚠️

`users.email` 有唯一索引，写入时**必须存真 NULL 而不是空字符串**（空串彼此相等，第二个无邮箱用户会撞唯一键）。这条在《数据模型字段详解》第二节已写明，P2 的注册接口是它第一次真正生效的地方。

</aside>

### 2. access / refresh 存哪里

| 令牌 | 有效期 | 存放位置 | 理由 |
| --- | --- | --- | --- |
| `access` | **15 分钟** | `localStorage`，key `quire_access_token` | 需要在 axios 拦截器里同步读出来塞进 `Authorization` 头，必须是 JS 可读的。短有效期把泄露窗口压到 15 分钟 |
| `refresh` | **7 天** | **httpOnly Cookie**，`Path=/api/v1/auth`、`SameSite=Lax`、生产加 `Secure` | JS 读不到，XSS 拿不走。`Path` 收窄后它只会跟着 `/auth/refresh` 与 `/auth/logout` 发出，不会附在每一个 `/entries` 请求上 |

**Cookie 方案的前提是同源**：生产走 Nginx 反代，前端静态与 `/api` 同域；开发走 Vite proxy（`/api` → `127.0.0.1:8000`，P0-5 已配好）。两边都是同源，所以不需要 `SameSite=None`，也不需要开 CORS 的 `credentials` 白名单——这正是选 Cookie 而不是「refresh 也塞 localStorage」的原因。

<aside>
📌

**为什么不把 `access` 也放 Cookie。** 那样等于自动附带凭据，CSRF 面立刻打开，得再加一套 CSRF token。而 `Authorization` 头是显式的，跨站页面无法伪造。**现在这套的攻击面是「XSS 能偷 15 分钟的 access」，可以接受；「refresh 被偷 7 天」不可接受**，所以只把后者藏进 httpOnly。

</aside>

轮换策略：`/auth/refresh` **每次都下发新的 refresh**（rotation），旧的立即失效。P2 不做黑名单表（那需要 Redis 或一张 `refresh_tokens` 表），改用 `users` 上的一个**新字段 `token_version`（INT，默认 0）**：

- refresh 的 payload 里带 `tv`，校验时必须等于库里的 `token_version`
- 「登出所有设备」「改密码」只需 `token_version += 1`，全部旧 refresh 一次作废
- 这是 P2 唯一需要的 `users` 表变更，一条 Alembic 迁移，`ALTER TABLE users ADD token_version INT NOT NULL DEFAULT 0`

JWT 载荷（`python-jose`，HS256，密钥 `JWT_SECRET`）：

```json
{
  "sub": "0198f2a1-4b3c-7000-8000-abcdef123456",
  "typ": "access",
  "tv": 0,
  "iat": 1788000000,
  "exp": 1788000900
}
```

`typ` 必须校验：**拿 refresh 当 access 用要被拒**，否则 7 天的令牌等于 7 天的 access。

### 3. 游客态本地数据怎么归属到 user_id

这是本节最容易造成数据丢失的一步，所以定得很死。

新增 `meta` 表两个键（`meta` 表 P1-1 就建好了，无 schema 变更）：

| key | 值 | 语义 |
| --- | --- | --- |
| `ownerUserId` | `""` 或 UUID | 这个浏览器库里的数据**属于谁**。`""` = 游客态，从未登录过 |
| `lastSyncAt` | `""` 或 ISO | pull 游标。**只在 bootstrap 全部 push 成功后**才第一次写值 |

登录成功后的分支只有三种，没有第四种：

1. **`ownerUserId === ""`（游客首登，最常见）** → 走 `claimLocalData()`：先强制「防蠹」导出，再把 `entries` / `tags` / `media` 三张表**全部置 `dirty = 1`**，写入 `ownerUserId`，然后**只 push**。push 全部 200 之后才写 `lastSyncAt`，此后才允许 pull。
2. **`ownerUserId === 登录用户`**（同一账号回来） → 正常 `push → pull` 循环，什么都不用做。
3. **`ownerUserId !== 登录用户`**（换账号） → **拒绝，不混库**。弹一个只有两条出路的对话框：「导出防蠹备份并清空本地，以新账号重新开始」或「取消登录」。**绝不合并两个用户的数据**——合并意味着把 A 的日记写进 B 的 `user_id`，不可逆。

```tsx
// src/api/claim.ts —— 游客数据认领。只在登录成功后调用一次。
import { db } from "@/db/schema"
// @/repo 里没有 exportBackup（P1-5 导出的是 backupRepo.exportAll，而落盘在 capabilities）。
// 两步包成一个函数，见本页第十一节 N2。
import { downloadFullBackup } from "@/capabilities/backupFile"
import { utcNow } from "@/shared/time"

export type ClaimResult =
  | { kind: "claimed"; entries: number; tags: number; media: number }
  | { kind: "sameOwner" }
  | { kind: "ownerMismatch"; localOwner: string }

async function readMeta(key: string): Promise<string> {
  const row = await db.meta.get(key)
  return typeof row?.value === "string" ? row.value : ""
}

export async function claimLocalData(userId: string): Promise<ClaimResult> {
  const owner = await readMeta("ownerUserId")
  if (owner && owner === userId) return { kind: "sameOwner" }
  if (owner && owner !== userId) return { kind: "ownerMismatch", localOwner: owner }

  // 硬约束第 3 条：认领前先落一份防蠹备份，失败就整个中止（不捕异常）。
  await downloadFullBackup()

  const counts = await db.transaction("rw", db.entries, db.tags, db.media, db.meta, async () => {
    const e = await db.entries.toCollection().modify({ dirty: 1 })
    const t = await db.tags.toCollection().modify({ dirty: 1 })
    const m = await db.media.toCollection().modify({ dirty: 1 })
    await db.meta.put({ key: "ownerUserId", value: userId })
    // 注意：这里不写 lastSyncAt。游标只能在 bootstrap 的 push 全部成功后才写。
    await db.meta.put({ key: "claimedAt", value: utcNow() })
    return { entries: e, tags: t, media: m }
  })

  return { kind: "claimed", ...counts }
}
```

<aside>
🔒

**`claimLocalData` 里绝不能出现任何 `db.*.clear()` 或 `delete`**。它只做三件事：导出备份、把 dirty 全部拉高、写 owner。**换账号的清库动作放在另一个函数里**（`resetLocalForNewOwner()`），并且必须由用户在对话框上显式点确认才调用——两个动作写在同一个函数里，早晚会被误调。

</aside>

后端认证端点：

| 方法 | 路径 | 请求 | `data` |
| --- | --- | --- | --- |
| POST | `/api/v1/auth/register` | `{email, password, timezone}` | `{user, access_token, expires_in}`  • `Set-Cookie` |
| POST | `/api/v1/auth/login` | `{email, password}` | 同上 |
| POST | `/api/v1/auth/refresh` | 无 body（读 Cookie） | `{access_token, expires_in}`  • 新 `Set-Cookie` |
| POST | `/api/v1/auth/logout` | 无 | `null`，并清 Cookie |
| GET | `/api/v1/auth/me` | 需 `Authorization` | `{user}` |

`timezone` 注册时由前端传 `Intl.DateTimeFormat().resolvedOptions().timeZone`。它在 P2 依然不参与任何存储与展示（存储永远 UTC），只是把值先收上来，P5 的签到与 P4 的日程提醒要用。

## 三、② Entry / Tag / Media 三类 REST 契约

### 1. 三条全局约定

1. **写操作一律 `PUT /{资源}/{id}`，不用 `POST` 创建。** id 是前端生成的 UUID v7（P1-1 起就是），所以「创建」和「更新」在语义上都是 upsert。这样重试、同步重放、用户双击全部天然幂等——这是离线优先应用能少写一整套去重逻辑的关键。
2. **响应体永远 `{code, message, data}`**。`code = 0` 表示成功，非 0 是业务错误码；HTTP 状态码同时保持语义正确（401 / 403 / 404 / 422），**两者都要对**，前端拦截器靠 HTTP 状态判断 401，靠 `code` 判断业务失败。
3. **线上字段 snake_case**，前端类型 camelCase，**转换只允许出现在 `src/api/` 里**。`src/shared/types.ts` 保持现在的 camelCase 不动（铁律 6：shared 是纯 TS，将来小程序端复用同一份），`@/repo` 之上的所有代码看不到 snake_case。

### 2. 分页（P0-3 推过来的那条）

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "items": [],
    "total": 0,
    "page": 1,
    "page_size": 20
  }
}
```

- 参数名 `page`（从 1 开始）/ `page_size`（默认 20，**上限 100**）
- **形状与 P1-1 的 `PagedNOTION_MARKDOWN_ESCAPED_LT_SENTINELT&gt;` 完全一致**（`items / total / page / pageSize`），只差命名风格。这不是巧合，是 P1-1 当初照着后端形状定的，现在正好省掉一层适配
- `total` 走单独一条 `SELECT COUNT(*)`，不用 `SQL_CALC_FOUND_ROWS`（8.0 已废弃）

```python
# app/api/deps.py —— 统一分页依赖，所有列表接口都用它
from dataclasses import dataclass

from fastapi import Query

MAX_PAGE_SIZE = 100

@dataclass(frozen=True)
class Pagination:
    page: int
    page_size: int

    @property
    def offset(self) -> int:
        return (self.page - 1) * self.page_size

def pagination(
    page: int = Query(1, ge=1),
    page_size: int = Query(20, ge=1, le=MAX_PAGE_SIZE),
) -> Pagination:
    return Pagination(page=page, page_size=page_size)
```

```python
# app/schemas/envelope.py —— 统一响应体。全项目只有这一处构造 {code,message,data}
from typing import Generic, TypeVar

from pydantic import BaseModel

T = TypeVar("T")

class Envelope(BaseModel, Generic[T]):
    code: int = 0
    message: str = "ok"
    data: T | None = None

class Page(BaseModel, Generic[T]):
    items: list[T]
    total: int
    page: int
    page_size: int

def ok(data: T | None = None) -> Envelope[T]:
    return Envelope[T](code=0, message="ok", data=data)

def paged(items: list[T], total: int, page: int, page_size: int) -> Envelope[Page[T]]:
    return ok(Page[T](items=items, total=total, page=page, page_size=page_size))
```

### 3. Entry

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/entries` | 查询参数：`page`、`page_size`、`keyword`、`tag_id`、`date_from`、`date_to`、`only_deleted`、`order`（`entry_date_desc` | `entry_date_asc` | `updated_at_desc`）。参数名与 `EntryListParams` 一一对应 |
| GET | `/api/v1/entries/{id}` | 单篇，含 `content` |
| PUT | `/api/v1/entries/{id}` | **幂等 upsert**，body 见下 |
| DELETE | `/api/v1/entries/{id}` | **软删除**，body `{client_updated_at}`，写 `deleted_at` |

请求体（`PUT`）：

```json
{
  "entry_date": "2026-09-04",
  "sort_order": 0,
  "title": "第一篇",
  "content": { "schemaVersion": 1, "doc": { "type": "doc", "content": [] } },
  "content_text": "今天去旅行了",
  "mood": "happy",
  "weather": "sunny",
  "tag_ids": ["0198f2a1-...", "0198f2a2-..."],
  "from_schedule_id": null,
  "client_updated_at": "2026-09-04T13:20:09.755Z",
  "deleted_at": null
}
```

四个细节：

- **`content_text` 由客户端一并传，服务端不重算**。理由：抽取规则的唯一实现在 `src/shared/text.ts`，服务端再写一份 Python 版必然漂移（P1-6 L 节刚因为 alt 进纯文本踩过一次）。服务端只做兜底：`content_text` 缺失时存空串，不猜。
- **`tag_ids` 是全量覆盖语义**。服务端在同一事务里 `DELETE FROM entry_tags WHERE entry_id = ?` 再批量插入。本地存数组、服务端存中间表，展平就在这里发生（P1-1 第 8 节早写好了这个分工）。
- **`client_updated_at` 必填**，缺了直接 422。它是第 3 节冲突仲裁的唯一依据，允许它为空等于允许冲突无法判定。
- `content` 里的 `schemaVersion` 保持 camelCase：它是**文档内部**的字段，不是 API 字段，snake_case 规则不穿透到 JSON 正文里。

### 4. Tag

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/tags` | 全量返回，**不分页**（个人标签量级几十条，分页只会让前端多写一层循环） |
| PUT | `/api/v1/tags/{id}` | upsert，body `{name, color, created_at}` |

**标签没有软删除、也不可改名**（《数据模型字段详解》第四节已定）。因此 `tags` 表连 `updated_at` 都没有，同步策略退化成最简单的一种：**只上行、只新增，永不删除**。

`uk_user_name` 唯一约束会带来一个必须处理的情况：**两台设备各自离线建了同名标签**，两个不同的 UUID。服务端的处理是 **409 + 返回既存的 tag**（`data: {id, name}`），客户端收到 409 后**把本地那条改指到服务端的 id**：更新所有引用了旧 id 的 `entries.tagIds`，删掉本地旧 tag，并把受影响的 entry 置 `dirty = 1`。这段归并逻辑与 P1-5 导入 JSON 时的「同名标签归并」是同一个函数，复用即可。

### 5. Media

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/media/{id}` | **multipart 上传**。表单字段：`file`（原图，必填）、`thumb`（缩略图，可选）、`entry_id`、`sort_order`、`width`、`height`、`created_at`。返回 `{id, url, thumb_url}` |
| GET | `/api/v1/media` | 元数据列表（**不含二进制**），参数 `entry_id` 或 `since` |
| DELETE | `/api/v1/media/{id}` | 删元数据与文件 |

用 `POST /{id}` 而不是 `PUT` 只有一个原因：multipart 重传整个文件代价大，服务端在这里做**「已存在则直接返回既有 url、不重写文件」**的短路，语义上不是纯 upsert。id 由前端给，所以重复上传依然安全。

限制：单文件 **10 MB**（P1-6 边界测试的上限就是 10MB 图），MIME 白名单 `image/jpeg` / `image/png` / `image/webp` / `image/gif`。**落盘文件名用 `{media_id}.{ext}`，绝不用原始文件名**（路径穿越 + 中文名编码 + P1-6 L 节刚把 `alt` 里的文件名清掉，不该在服务端又捡回来）。

### 6. 同步专用端点

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/sync/push` | 批量 upsert。body `{entries: [], tags: [], media_meta: []}`，**每类单批上限 50**。返回逐条结果与 `server_time` |
| GET | `/api/v1/sync/changes` | 增量拉取。参数 `since`（ISO，UTC）、`limit`（默认 200）。返回三类变更 + `server_time`  • `has_more` |

`/sync/push` 的返回**必须是逐条的**，不能整批成功或失败：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "server_time": "2026-09-04T13:20:11.002Z",
    "entries": [
      { "id": "0198f2a1-...", "status": "applied" },
      { "id": "0198f2a2-...", "status": "stale", "server_client_updated_at": "2026-09-04T14:00:00.000Z" },
      { "id": "0198f2a3-...", "status": "error", "message": "content_text too long" }
    ],
    "tags": [],
    "media_meta": []
  }
}
```

三种状态各自的客户端动作：`applied` → 置 `dirty = 0`；`stale` → **保持 `dirty = 1`**，交给随后的 pull 去仲裁；`error` → 保持 `dirty = 1` 并记进 `meta.syncErrors`，**不重试超过 3 次**（否则一条坏数据会把整个同步循环永久卡住，这是同步系统最常见的死法）。

`/sync/changes` 用 `updated_at` 做游标，走 `idx_user_updated` 索引（P0 建表时就为这一个查询留的）。**游标必须用服务端返回的 `server_time`，绝不用客户端本地时间**——两边时钟差几秒就会漏数据，而且漏得静默。

## 四、③ dirty 位的同步循环与冲突策略

### 1. 何时推、何时拉

**顺序永远是 push 然后 pull，绝不并行、绝不颠倒。** 颠倒的后果正是硬约束里禁止的那件事：先拉到服务端的旧版本盖掉本地新版本，再把被盖掉的内容推上去，两台设备一起丢改动。

触发点五个，全部汇到同一个 `runSync()`，内部用一个 `running` 标志做互斥（同时最多一个同步在跑）：

| 触发 | 时机 | 备注 |
| --- | --- | --- |
| 登录成功 | 一次 | 首登走 bootstrap（只 push） |
| 写操作后 | **5 秒 debounce** | 编辑器已经有 800ms 节流的本地保存，同步再退一档，避免每敲一个字发一次请求 |
| `visibilitychange` → 可见 | 每次回前台 | 与 P1-6 的 D1 flush 复用同一个监听（**先 flush 本地保存，再 `runSync`**，顺序不能反） |
| `online` 事件 | 每次网络恢复 | 断网期间攒的 dirty 一次清掉 |
| 兜底轮询 | **5 分钟** | 只在页面可见时跑，后台标签页不轮询 |

**P2 不做 WebSocket、不做长轮询。** 单人多设备场景下秒级实时毫无价值，而它会带来连接保活、鉴权续期、断线重连三块新代码。

### 2. 冲突以谁为准

由第 6 条（本地优先）直接推导，规则只有三行，且**没有例外**：

1. 比较双方的 **`client_updated_at`**，**大的赢**（谁后编辑谁赢，不是谁后同步谁赢）。
2. **时间戳完全相等 → 本地赢**，不写库、直接置 `dirty = 0`。这条是本地优先的落点。
3. **本地 `dirty = 1` 的记录，pull 阶段永不覆盖。** 服务端版本存进 `meta.conflicts`（保留 30 天）以备排查，正文一律不动。

服务端在 `PUT` / `push` 时做同样的比较：入参的 `client_updated_at` 不大于库里的值就**不写**，返回 `stale`。这样两端用的是同一把尺子，不需要额外的版本号或向量时钟。

<aside>
📌

**为什么不做字段级合并。** 日记正文是一整棵 Tiptap 文档树，字段级合并对它没意义（合并两个 `content` 只能得到乱码）。真正的协同编辑需要 CRDT / OT，那是量级完全不同的工程，而单人多设备的实际冲突率极低。**P2 明确采用整条记录粒度的 last-writer-wins**，并靠第 3 行规则保证「输的那一方仍能被找回」。

</aside>

### 3. 软删除怎么同步

**`isDeleted` 与 `deletedAt` 当普通字段同步，走完全相同的仲裁规则**，没有特殊通道。

两端的字段分工（P1-1 定的形状，P2 不改）：

| 本地（IndexedDB） | 服务端（MySQL） | 说明 |
| --- | --- | --- |
| `isDeleted: 0 | 1` | —— | **本地专有**，只为绕开「IndexedDB 不索引 null」（铁律 4） |
| `deletedAt: Iso | null` | `deleted_at DATETIME(3)` | **线上只传这一个**。服务端 `deleted_at IS NOT NULL` 即已删 |

所以 `src/api/` 的映射层要做一次转换：上行时 `isDeleted` **不传**，只传 `deletedAt`；下行时按 `deleted_at !== null` 反推 `isDeleted = 1`。**两个字段都传是错的**——它们会不一致，而不一致时不知道该信谁。

三条墓碑规则：

1. **服务端永不物理删除 `diary_entries` 的行。** 直接删行的话，其他设备只能看到「服务端没这条」，而那与「本地新建还没上传」无法区分，结果是删除被回滚（《数据模型字段详解》第三节第 4 点已推导过）。
2. **`entryRepo.purge()`（断简里的「弃去 / 尽弃」）在 P2 语义变了**：登录态下不能直接 `db.entries.delete()`，否则墓碑消失、下次 pull 会把这条从服务端拉回来（「删了又回来」是同步类 bug 里最刺眼的一种）。改法是**保留一条只剩骨架的墓碑记录**（清空 `content` / `contentText` / `title`，保留 id、`deletedAt`、`dirty=1`），推上去之后再本地删。
3. 服务端**物理清理只在一处**：定时任务删 `deleted_at` 超过 **180 天**的行。180 天远大于回收站的 30 天窗口，且大于任何合理的「某台设备离线多久」。

### 4. 同步引擎骨架

```tsx
// src/api/sync.ts —— 唯一的同步入口。上层只调 runSync()，不碰内部函数。
import { db } from "@/db/schema"
import { pullChanges, pushBatch } from "@/api/endpoints"
import {
  fromWireEntry,
  fromWireTag,
  mediaPatchFromWire,
  toWireEntry,
  toWireMediaMetaPush,
  toWireTag,
} from "@/api/mappers"
import type { WireMediaMeta, WireTag } from "@/api/wire"
import { utcNow } from "@/shared/time"
import type { Entry } from "@/shared/types"

const BATCH = 50
const MAX_ERRORS = 3

let running = false

async function meta(key: string): Promise<string> {
  const row = await db.meta.get(key)
  return typeof row?.value === "string" ? row.value : ""
}

/** 上行：把所有 dirty=1 的记录分批推上去。返回服务端时间。 */
async function pushAll(): Promise<string> {
  let serverTime = ""
  for (;;) {
    const entries = await db.entries.where("dirty").equals(1).limit(BATCH).toArray()
    const tags = await db.tags.where("dirty").equals(1).limit(BATCH).toArray()
    const mediaMeta = await db.media.where("dirty").equals(1).limit(BATCH).toArray()
    if (!entries.length && !tags.length && !mediaMeta.length) break

    // 三类都要过映射层。裸传本地行会撞两件事：字段名是 camel 的（Tag.createdAt
    // 对不上 created_at），以及 MediaItem 里带 blob / thumbBlob。
    const res = await pushBatch({
      entries: entries.map(toWireEntry),
      tags: tags.map(toWireTag),
      mediaMeta: mediaMeta.map(toWireMediaMetaPush),
    })
    serverTime = res.serverTime

    // 逐条处理：只有 applied 才清 dirty。stale 留给随后的 pull 仲裁。
    await db.transaction("rw", db.entries, db.tags, db.media, async () => {
      for (const r of res.entries) {
        if (r.status === "applied") await db.entries.update(r.id, { dirty: 0 })
        else if (r.status === "error") await noteError("entry", r.id, r.message)
      }
      for (const r of res.tags) {
        if (r.status === "applied") await db.tags.update(r.id, { dirty: 0 })
      }
      for (const r of res.mediaMeta) {
        if (r.status === "applied") await db.media.update(r.id, { dirty: 0 })
      }
    })

    // 全批都不是 applied 说明没有推进，跳出避免死循环。
    // 必须三类一起看：只看 entries 的话，「只有标签脏了」的那一轮会被误判成没推进。
    const progressed =
      res.entries.some((r) => r.status === "applied") ||
      res.tags.some((r) => r.status === "applied") ||
      res.mediaMeta.some((r) => r.status === "applied")
    if (!progressed) break
  }
  return serverTime
}

/** 下行：拉增量。dirty=1 的本地记录一律不覆盖。 */
async function pullAll(since: string): Promise<string> {
  let cursor = since
  for (;;) {
    const res = await pullChanges({ since: cursor, limit: 200 })

    await db.transaction("rw", db.entries, db.tags, db.media, db.meta, async () => {
      for (const wire of res.entries) {
        const incoming: Entry = fromWireEntry(wire)
        const local = await db.entries.get(incoming.id)

        if (!local) {
          await db.entries.put({ ...incoming, dirty: 0 })
          continue
        }
        // 规则 3：本地有未同步改动，服务端版本只进冲突缓冲。
        if (local.dirty === 1) {
          await stashConflict(incoming)
          continue
        }
        // 规则 1 与 2：client_updated_at 大的赢；相等则本地赢（不写）。
        if (incoming.clientUpdatedAt > local.clientUpdatedAt) {
          await db.entries.put({ ...incoming, dirty: 0 })
        }
      }
      // tags 只新增不删；media 只更新元数据与 remoteUrl，Blob 永不被下行覆盖。
      await mergeTags(res.tags)
      await mergeMediaMeta(res.mediaMeta)
    })

    cursor = res.serverTime
    if (!res.hasMore) break
  }
  await db.meta.put({ key: "lastSyncAt", value: cursor })
  return cursor
}

export async function runSync(): Promise<void> {
  if (running) return
  if (!(await meta("ownerUserId"))) return // 游客态不同步
  running = true
  try {
    const serverTime = await pushAll()
    const since = await meta("lastSyncAt")

    // 硬约束第 1 条：bootstrap（lastSyncAt 为空）这一轮只 push。
    // 游标先写成本次 push 的服务端时间，下一轮才开始 pull。
    if (!since) {
      await db.meta.put({ key: "lastSyncAt", value: serverTime || utcNow() })
      return
    }
    await pullAll(since)
  } finally {
    running = false
  }
}

async function noteError(kind: string, id: string, message?: string): Promise<void> {
  const row = await db.meta.get("syncErrors")
  const list = Array.isArray(row?.value) ? (row.value as Array<Record<string, unknown>>) : []
  const hit = list.find((x) => x.id === id)
  const count = typeof hit?.count === "number" ? hit.count + 1 : 1
  const next = list.filter((x) => x.id !== id)
  if (count <= MAX_ERRORS) next.push({ kind, id, message, count, at: utcNow() })
  await db.meta.put({ key: "syncErrors", value: next })
}

async function stashConflict(incoming: Entry): Promise<void> {
  const row = await db.meta.get("conflicts")
  const list = Array.isArray(row?.value) ? (row.value as unknown[]) : []
  list.push({ at: utcNow(), server: incoming })
  await db.meta.put({ key: "conflicts", value: list.slice(-100) })
}

/**
 * 标签：只新增，永不删、永不改名（《数据模型字段详解》第四节）。
 * 所以同 id 就是同一条，不需要比时间、也不需要 update。
 */
async function mergeTags(rows: WireTag[]): Promise<void> {
  for (const w of rows) {
    if (await db.tags.get(w.id)) continue
    // 同名不同 id：不在下行里处理。它由 push 的 409 分支做归并（第三节 4 小节），
    // 因为只有那里才知道要把本地哪些 entry 的 tagIds 改指向。
    if (await db.tags.where("name").equals(w.name).first()) continue
    await db.tags.put(fromWireTag(w))
  }
}

/**
 * 图片：只写元数据与远端地址，blob / thumbBlob 一个字节都不动。
 * 下行覆盖本地 Blob 等于用网络图换掉原图，既慢又可能降质。
 */
async function mergeMediaMeta(rows: WireMediaMeta[]): Promise<void> {
  for (const w of rows) {
    const patch = mediaPatchFromWire(w)
    const local = await db.media.get(w.id)
    if (local) {
      await db.media.update(w.id, patch)
      continue
    }
    // 本地没有这张（新设备）：先只落元数据占位，真正的 Blob 由
    // LocalImageView 的三级回退按需回填（第五节）。0 字节 = 尚未回填。
    await db.media.put({
      id: w.id,
      blob: new Blob([], { type: w.mime }),
      thumbBlob: null,
      mime: w.mime,
      width: w.width,
      height: w.height,
      size: w.size,
      createdAt: w.created_at,
      dirty: 0,
      ...patch,
    })
  }
}
```

<aside>
⚠️

`mergeTags` / `mergeMediaMeta` **的实现就在上面代码块的末尾**（旧版把它们留空，于是落码必然报两条 `TS2304`；第十三节 K1）。语义定死如下：**`mergeTags` 只新增，遇到同名不同 id 走第三节第 4 点的归并**；**`mergeMediaMeta` 只写 `remoteUrl` / `thumbRemoteUrl` / `entryId` / `sortOrder`，绝不动 `blob` 与 `thumbBlob`**。下行覆盖本地 Blob 等于用网络图换掉原图，既慢又可能丢质量。

</aside>

## 五、④ 图片上传与 local:// ↔ remoteUrl 双轨

### 1. 铁律 5 在 P2 一字不改

**正文 JSON 里的 `src` 永远是 `local://media/{id}`**。上云之后也不改、不批量替换、不写迁移脚本。

这正是 P1 那个设计的回报：图片上云只需要往 `media` 表的一行里填 `remoteUrl`，**一篇日记的正文都不用碰**。反过来，如果当初把真实地址写进了正文，P2 就得写一个遍历所有日记、递归遍历 JSON 树、替换 `src` 的迁移，并且要在每台设备上都恰好执行一次——那是个几乎不可能做对的事。

### 2. 渲染的三级回退

`LocalImageView.vue`（P1-3 / P1-6 已有）在 P2 只加一条回退，解析 `local://media/{id}` 之后：

1. 本地有 `blob` → `createObjectURL`，**优先本地**（快、不耗流量、离线可用）
2. 本地没有但 `remoteUrl` 有值 → 直接用远程地址，**并在后台把原图下载回来补进 IndexedDB**（补完下次就走第 1 条）
3. 两者都没有 → 显示占位图与「此图未同步」

第 2 条的后台回填是新设备的主路径：登录后先拉到元数据与远程地址，图片按需逐张回本地，而不是一次把几百 MB 全下来。

### 3. 缩略图上不上云：**上云**

定案**上云**，新增服务端字段 `media.thumb_url`（P0 建表时就有这一列，无迁移）与本地字段 `thumbRemoteUrl`。

| 方案 | 结论 |
| --- | --- |
| 缩略图不上云，新设备下原图后本地生成 | ❌ 列表页首图是**首屏就要显示**的东西。新设备打开成编，为了几十个 40 KB 的缩略图去下几十兆原图，移动流量下不可接受 |
| **缩略图上云** | ✅ 与原图**同一次 multipart 请求**传完，不多一轮往返。缩略图仍**只在客户端生成**（P1-6 批次 B 的 `thumbBlob` 已经在做），服务端不装图片处理库、不做任何转码 |

服务端对缩略图只做两件事：存文件、把地址写进 `thumb_url`。**不校验它是不是真的比原图小、不重新生成**——那会引入 Pillow 依赖和一堆格式边界，收益为零。

### 4. P2 的存储落点：服务器本地磁盘，不是 OSS

| 项 | P2 定案 |
| --- | --- |
| 落盘目录 | `/var/lib/quire/media/{yyyy}/{mm}/{media_id}.{ext}`，缩略图同目录 `{media_id}_thumb.{ext}` |
| 对外地址 | **Nginx 直接 `alias` 静态服务**，不经过 FastAPI（Python 转发静态文件纯属浪费） |
| 库里存什么 | **相对路径** `/media/2026/09/{id}.jpg`，**不存带域名的绝对地址** |
| 鉴权 | P2 **不做签名 URL**。地址里是 UUID v7，不可枚举；单人自用阶段够了 |
| 迁 OSS | 推 P3。因为库里存的是相对路径，届时只需改 Nginx 或加一个 CDN 前缀，**数据不用动** |

<aside>
📌

**存相对路径而不是绝对 URL**，是这一节唯一有长期影响的决定。存了 `https://xxx.com/media/...`，将来换域名、上 CDN、迁 OSS 都要 `UPDATE` 全表；存相对路径则只改一处配置。前端拼接放在 `src/api/mappers.ts` 一个函数里。

</aside>

## 六、⑤ src/api/request.ts

### 1. 三个要点

1. **`baseURL` 走 `import.meta.env.VITE_API_BASE_URL`**。P1-6 批次 I 落的两个 env 文件里已经是 `/api/v1`（无域名、无密钥），开发靠 Vite proxy、生产靠 Nginx 反代，**两边都是同源**——这也是第二节 refresh Cookie 方案成立的前提。
2. **401 走 single-flight 刷新队列。** 同步循环会并发发多个请求，access 过期时它们会**同时**拿到 401。不做 single-flight 的后果是并发刷新 N 次，而 refresh 是**轮换**的（每次下发新的、旧的作废），于是后到的刷新拿着已作废的 refresh 失败，用户被莫名踢下线。这个 bug 只在多请求并发时出现，单请求手测永远碰不到。
3. **token key 统一 `quire_access_token`**。`request.ts` 里现存**两处** `qingjian_access_token`（P0 脚手架时期的旧名，索引页第六节已记录改名决定），本次**直接删掉旧名，不做兼容读取**——P1 从未写过这个 key，库里根本没有旧值可兼容。

### 2. src/api/tokenStore.ts

```tsx
/**
 * access token 的唯一存取点。
 *
 * key 只有 quire_access_token 一个。旧名 qingjian_access_token 已在 P2 彻底删除，
 * 不做兼容读取：P1 阶段从未登录、从未写过这个 key，localStorage 里不存在旧值。
 */
const ACCESS_TOKEN_KEY = "quire_access_token"

let cached: string | null = null

export function getAccessToken(): string {
  if (cached !== null) return cached
  cached = localStorage.getItem(ACCESS_TOKEN_KEY) ?? ""
  return cached
}

export function setAccessToken(token: string): void {
  cached = token
  if (token) localStorage.setItem(ACCESS_TOKEN_KEY, token)
  else localStorage.removeItem(ACCESS_TOKEN_KEY)
}

export function clearAccessToken(): void {
  setAccessToken("")
}

/** refresh token 不在这里——它是 httpOnly Cookie，JS 读不到也不该读。 */
```

### 3. src/api/request.ts（整文件）

```tsx
import axios, {
  AxiosError,
  type AxiosInstance,
  type AxiosResponse,
  type InternalAxiosRequestConfig,
} from "axios"

import { clearAccessToken, getAccessToken, setAccessToken } from "./tokenStore"

/** 后端统一响应体。code === 0 才是成功。 */
export interface Envelope<T> {
  code: number
  message: string
  data: T
}

/**
 * 不能用构造函数参数属性（public code: number）。
 *
 * Vite 7 的 Vue-TS 模板默认开了 erasableSyntaxOnly，它只允许「抹掉类型就等价」
 * 的语法。参数属性、enum、namespace 都会生成运行时代码，因此一律报 TS1294。
 * 字段显式声明 + 构造函数里手写赋值，行为完全一致。
 */
export class ApiError extends Error {
  readonly code: number
  readonly status?: number

  constructor(code: number, message: string, status?: number) {
    super(message)
    this.name = "ApiError"
    this.code = code
    this.status = status
  }
}

type RetriableConfig = InternalAxiosRequestConfig & { _retried?: boolean }

export const http: AxiosInstance = axios.create({
  // 开发走 Vite proxy、生产走 Nginx 反代，两者都是同源，所以这里只有路径。
  baseURL: import.meta.env.VITE_API_BASE_URL,
  timeout: 20_000,
  // refresh token 是 httpOnly Cookie，必须带上凭据才发得出去。
  withCredentials: true,
})

http.interceptors.request.use((config) => {
  const token = getAccessToken()
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

// ---- single-flight 刷新 ----------------------------------------------------
// 同步循环会并发发请求，access 过期时它们会同时拿到 401。
// 若每个都去刷新，而 refresh 又是轮换的（每次下发新的、旧的立即作废），
// 后到的刷新必然失败，用户会被莫名踢下线。所以全局只允许有一个刷新在飞。
let refreshing: Promise<string> | null = null

async function refreshAccessToken(): Promise<string> {
  if (refreshing) return refreshing

  refreshing = (async () => {
    try {
      // 用裸 axios，绕开本实例的拦截器，避免刷新自身 401 时递归。
      const res = await axios.post<Envelope<{ access_token: string }>>(
        "/auth/refresh",
        null,
        { baseURL: import.meta.env.VITE_API_BASE_URL, withCredentials: true },
      )
      const token = res.data?.data?.access_token ?? ""
      if (!token) throw new ApiError(-1, "refresh 未返回 access_token", 401)
      setAccessToken(token)
      return token
    } catch (e) {
      clearAccessToken()
      onUnauthorized?.()
      throw e
    } finally {
      refreshing = null
    }
  })()

  return refreshing
}

/** 刷新彻底失败时的回调，由路由层注入（跳登录页）。此处不 import router。 */
let onUnauthorized: (() => void) | null = null

export function setUnauthorizedHandler(fn: () => void): void {
  onUnauthorized = fn
}

http.interceptors.response.use(
  (res: AxiosResponse<Envelope<unknown>>) => {
    const body = res.data
    // 有 code 字段就按统一响应体校验；文件流等无 envelope 的响应原样放过。
    if (body && typeof body.code === "number" && body.code !== 0) {
      throw new ApiError(body.code, body.message || "请求失败", res.status)
    }
    return res
  },
  async (error: AxiosError<Envelope<unknown>>) => {
    const config = error.config as RetriableConfig | undefined
    const status = error.response?.status

    // 401 且未重放过 → 刷新一次，然后原样重放。
    // 刷新端点自身的 401 不进这里（它用的是裸 axios）。
    if (status === 401 && config && !config._retried) {
      config._retried = true
      try {
        const token = await refreshAccessToken()
        config.headers.Authorization = `Bearer ${token}`
        return http.request(config)
      } catch {
        // 落到下面统一抛错，不再重试。
      }
    }

    const body = error.response?.data
    if (body && typeof body.code === "number") {
      throw new ApiError(body.code, body.message || error.message, status)
    }
    throw new ApiError(-1, error.message || "网络异常", status)
  },
)

/** 业务层只用这四个，永远拿到已解包的 data。 */
export async function get<T>(url: string, params?: unknown): Promise<T> {
  const res = await http.get<Envelope<T>>(url, { params })
  return res.data.data
}

export async function post<T>(url: string, body?: unknown): Promise<T> {
  const res = await http.post<Envelope<T>>(url, body)
  return res.data.data
}

export async function put<T>(url: string, body?: unknown): Promise<T> {
  const res = await http.put<Envelope<T>>(url, body)
  return res.data.data
}

export async function del<T>(url: string, body?: unknown): Promise<T> {
  const res = await http.delete<Envelope<T>>(url, { data: body })
  return res.data.data
}
```

<aside>
⚠️

**两个容易写错的地方。**

① 刷新请求必须用**裸 `axios` 而不是 `http`**，否则刷新自身返回 401 时会再次进入响应拦截器，无限递归。

② `request.ts` **不许 `import router`**。router 会 import 视图、视图 import composable、composable 又回到 api 层，循环依赖在 Vite 里表现为运行时 `undefined`，极难定位。用 `setUnauthorizedHandler` 由路由层反向注入。

</aside>

## 七、⑥ 本地优先还是服务端优先

<aside>
🔑

**定案：本地优先（local-first）。IndexedDB 是权威副本，服务端是备份与多设备中转。**

</aside>

四条理由，按重要性排：

1. **P1 的全部工程都建立在这个前提上。** 主键前端生成、`client_updated_at` 客户端写、`entry_date` 客户端算、`dirty` 位、Repository 抽象——这五件事只在本地优先下才成立。改成服务端优先，等于把 P1-1 到 P1-6 的地基推掉重砌。
2. **它是唯一能满足硬约束的口径。** 服务端优先的第一次同步天然是「拉服务端覆盖本地」，而服务端此刻是空库——那正好是把 P1 数据全部清零。
3. **产品形态要求离线可用。** 日记是随手写的东西，地铁里没信号也得能写。
4. **单人多设备的冲突率极低**，last-writer-wins 足够；真正需要服务端仲裁的是多人协作，本项目没有。

代价说清楚，不含糊：

| 代价 | 表现 | P2 的应对 |
| --- | --- | --- |
| 全文检索仍在本地做 | MySQL 的 `ft_content`（ngram）在 P2 **用不上**，搜索继续走 P1-4 的 `includes` | 接受。ngram 索引留着，P3 做「全库云端搜索」时才启用 |
| 服务端不能拒绝「过期写入」以外的东西 | 客户端是权威，服务端基本只做存储 | 服务端仍校验格式与配额，只是不做业务仲裁 |
| 换设备首次要等回填 | 新设备要拉元数据、按需下图 | 第五节的三级回退：先显示远程图，后台补本地 |

**这一条是本页所有其他条目的上游。** 第 3 条的冲突策略、第 4 条的图片回退顺序、第 5 条 `repo/index.ts` 不做切换，全部是它的推论。**要改这一条，等于重写整个 P2。**

## 八、⑦ Redis 是否在 P2 启用

<aside>
🔴

**定案：P2 仍不启用。`REDIS_ENABLED=false` 保持当前生效，`/health` 继续返回 `"redis": "disabled"`**。

</aside>

清单页第六节列过 Redis 在本方案里的三个用途，逐条对照 P2：

| 用途 | P2 需要吗 | 说明 |
| --- | --- | --- |
| 验证码存储 | ❌ | 第二节已定 P2 不做验证码（邮箱 + 密码，无短信、无邮件验证） |
| 登录限流 | ⚠️ 需要，但不用 Redis | **进程内滑动窗口**即可：单 uvicorn 进程、单人自用。`{ip, email}` 维度，15 分钟内失败 10 次锁 15 分钟 |
| 签到缓存 | ❌ | 签到（上名青简）是 P5 |

另外两个「看起来该上 Redis」的地方也不上：

- **同步的并发控制**不需要分布式锁。互斥发生在**客户端**（`runSync()` 的 `running` 标志），服务端每个请求都是幂等 upsert，天然可重入。
- **refresh 黑名单**已用 `users.token_version` 解决（第二节），一个整数字段替掉一整个 Redis 依赖。

引入 Redis 的真实成本不是 `pip install`：是多一个必须开机自启、必须监控、必须备份决策（要不要持久化）、必须限制公网访问的服务。**在它能换来实际功能之前不装。** 触发条件写清楚，到点再装：

1. 开始做**验证码**（P3 手机号登录 / 邮箱找回密码），或
2. 开始做**签到连续天数**（P5），或
3. 后端**多进程 / 多机部署**——此时进程内限流失效，必须换成集中式

## 九、Dexie version 2 与新增字段（唯一的迁移债）

P2 需要动本地 schema，**现在做成本最低**（P1-6 批次 B 时的判断依然成立：库里只有测试数据）。

| 位置 | 变更 | 是否升 version |
| --- | --- | --- |
| `MediaItem` | 新增 `thumbRemoteUrl: string`（`""` = 未上云） | **否**。非索引字段 |
| `Entry` | 新增 `serverUpdatedAt: Iso \| ""`（服务端 `updated_at` 的回填，只用于排查，不参与仲裁） | **否**。非索引字段 |
| `db.version(2)` | `media` 索引加 `remoteUrl`（为「找出未上云的图」这个查询）；`entries` 索引不变 | **是**。新增索引必须升 version |
| `meta` | 新增四个键：`ownerUserId` / `lastSyncAt` / `syncErrors` / `conflicts` | **否**。`meta` 是 key-value 表 |
| `backup.ts` | **不升版本，保持 `BACKUP_FORMAT_VERSION = 2`**（下方纠正）。`BackupMedia extends Omit<MediaItem, "blob" | "thumbBlob">`，新字段**自动进出**；导入 v1 / v2 旧备份时缺字段补 `""` | **否**。见第十四节 J1 |
| MySQL `users` | 新增 `token_version INT NOT NULL DEFAULT 0`，期望列数 **9 → 10** | 一条 Alembic 迁移 |

```tsx
// src/db/schema.ts 的 version 2（在现有 version(1) 之后追加，不改 version(1)）
this.version(2)
  .stores({
    entries:
      "id, entryDate, updatedAt, isDeleted, dirty, *tagIds, [isDeleted+entryDate], [isDeleted+updatedAt]",
    tags: "id, name, dirty",
    media: "id, entryId, createdAt, dirty, remoteUrl",
    meta: "key",
  })
  .upgrade(async (tx) => {
    // 新增的都是非索引字段，Dexie 不会自动补默认值，读到 undefined 会让
    // "" 判断与 JSON 备份都出错，所以在 upgrade 里显式补齐。
    await tx.table("media").toCollection().modify((m) => {
      if (typeof m.remoteUrl !== "string") m.remoteUrl = ""
      if (typeof m.thumbRemoteUrl !== "string") m.thumbRemoteUrl = ""
    })
    await tx.table("entries").toCollection().modify((e) => {
      if (typeof e.serverUpdatedAt !== "string") e.serverUpdatedAt = ""
    })
  })
```

<aside>
⚠️

**`remoteUrl` 能进索引，是因为 P1-1 定的是空字符串而不是 `null`**（`MediaItem.remoteUrl: string`，注释写着「空字符串表示还没上云」）。要是当初写成 `null`，`where("remoteUrl").equals("")` 就会因为「IndexedDB 跳过 null 索引键」而永远返回空——铁律 4 的又一次生效。**新增的 `thumbRemoteUrl` 与 `serverUpdatedAt` 同样用 `""`，不用 `null`**。

</aside>

## 十一、N 节：第一次 npm run build 的十条报错（2026-09-04）

<aside>
🚦

**十条报错里只有三条是本页的错，其余七条是抢跑。**

`src/api/sync.ts`（P2-5）与 `src/repo/index.ts` 的改动被落盘在 `endpoints.ts` / `mappers.ts` / `session.ts`（P2-3）**之前**，所以 `TS2307 Cannot find module` 与 `TS2304 Cannot find name` 全部是预期内的「文件还没建」。

真正需要修本页的是 **N1 / N2 / N4** 三条，已就地改完（第二、六节的代码已是修正后的版本，直接重新拷一遍即可）。

</aside>

### N1  `erasableSyntaxOnly`：参数属性不能用（已修，第六节）

`TS1294` 两条都出在 `ApiError` 的 `public code` / `public status?`。Vite 7 模板的 `tsconfig.app.json` 默认开了 `erasableSyntaxOnly: true`，只允许「抹掉类型就等价」的语法。

**三个同类陷下次不要再踩**：`constructor(public x)` 参数属性、`enum`（改用 `as const` 对象 + `typeof` 取联合类型）、`namespace`。不要去关 `erasableSyntaxOnly` —— 小程序端将来也得能直接听这一层的 TS，保持可撦除是赚的。

### N2  `@/repo` 没有 `exportBackup`（已修，第二节）

P1-5 导出的是 `backupRepo.exportAll(onProgress?)`，它**只返回 `BackupFile` 对象**；序列化与落盘在 `SettingsView.vue` 里手写的（`JSON.stringify` + `saveBlob` + `backupFileName`）。现在认领流程也要导一份，同一段逻辑不得写两份，抽成能力层的一个函数：

```tsx
// src/capabilities/backupFile.ts（新建）—— 生成并落盘一份全量备份。
// 放 capabilities/ 而不是 shared/：它经由 saveBlob 碰 document（铁律 6）。
import { saveBlob } from "./download"
import { backupRepo } from "@/repo"
import { backupFileName } from "@/shared/backup"

export async function downloadFullBackup(
  onProgress?: (done: number, total: number) => void,
): Promise<{ entries: number; media: number }> {
  const file = await backupRepo.exportAll(onProgress)
  // 不传缩进：base64 本来就大，缩进只会让文件再胖一圈而没人会去读它。
  saveBlob(new Blob([JSON.stringify(file)], { type: "application/json" }), backupFileName())
  return { entries: file.counts.entries, media: file.counts.media }
}
```

`SettingsView.vue` 的导出按钮在 **P2-4** 顺手改成调 `downloadFullBackup`，只留进度文案与错误提示在页面里。**不要两处各改一半**。

### N3  铁律 7 对 `src/api/` 的适用范围

`claim.ts` 与 `sync.ts` 都直接 `import { db } from "@/db/schema"`，这**不算违反铁律 7**。铁律 7 约束的是「上层」：`views/`、组件、`composables/`。`src/api/` 与 `src/db/` 是**同级的基础设施层**，同步引擎必须能看到 `dirty` 位与事务，这些东西根本不在 repo 接口上。

### M3  `mediaMeta` 裸传（已修，第四节 + N6）——**这条是真雷**

第十一节 N6 的 callout ① 当时只写了一句「实施 P2-5 时要补」，把它留成了口头约定。现在编译器直接拦住了，**这是运气好**：

`MediaItem` 里有 `blob` 与 `thumbBlob`。如果这两个字段的名字恰好和线上契约撞上（比如将来给 `WireMediaMeta` 加个可选字段让类型侥幸通过），`JSON.stringify(blob)` 会得到 **`{}` 而且不报任何错**——整张原图变成一个空对象发上去，服务端存下 0 字节，本地看着一切正常（本地读的是 `blob` 字段）。这种 bug 要等到换设备下行时才现形，那时候原图早就没了。

所以修法不是「让类型过」，而是**把上行形状单独定死**：

| 方向 | 类型 | url / thumb_url |
| --- | --- | --- |
| 上行 `POST /sync/push` | `WireMediaMetaPush` | **不带**。客户端手上只有 `local://media/{id}`，地址是服务端落盘后才有的 |
| 下行 `GET /sync/changes` | `WireMediaMeta` | **带**。经 `mediaUrl()` 拼成可访问地址后写进 `remoteUrl` / `thumbRemoteUrl` |

`toWireMediaMetaPush()` **逐字段列出、不用 `{ ...m }` 展开**：这样以后给 `MediaItem` 加字段时，默认行为是「不上行」，而不是「悄悄上行」。

### 1. `src/shared/types.ts`：两个字段，一起加

<aside>
⚠️

**两个字段都写成必填（不加 `?`），于是所有「凭空造一条新行」的地方都会报 `TS2739` 缺字段。这是故意的**：`remoteUrl` 当年就是必填空串（铁律 4：IndexedDB 不索引 `null`，而 `remoteUrl` 在 version 2 里进了索引）。可选字段会让新行静默地存成 `undefined`，之后 `=== ""` 全部失效。

**先把造行的地方找全，再改**：

`rg -n "db\.entries\.(put|add)|db\.media\.(put|add)" frontend/src/`

预期命中：`db/entryRepo.ts`（`create`）、`db/mediaRepo.ts`（`attach`）、`db/backupRepo.ts`（`importAll`）。已写好的两处不用改：`mappers.ts` 的 `fromWireEntry` 已给 `serverUpdatedAt`，`sync.ts` 的 `mergeMediaMeta` 靠 `...patch` 带上 `thumbRemoteUrl`。

</aside>

### 2. `src/db/schema.ts`：version 2

代码就是第九节那一块，**原样追在现有 `version(1)` 之后**，`version(1)` 一个字不改（改了就不是迁移，是把旧库的升级路径抹掉）。

两件事要看清：

1. **只有 `media` 的索引变了**（末尾加 `remoteUrl`）。`entries` / `tags` / `meta` 三行必须**原样拄一遍**——Dexie 的 `stores()` 是**全量声明**，漏写一行就是删表。
2. `upgrade()` 里给存量行补 `""`。新增的是非索引字段，Dexie **不会**自动补默认值。

### 3. `src/shared/backup.ts` 与 `backupRepo.ts`：不升版本，只补回退

<aside>
🔑

**J1  纠正第九节的「`formatVersion` 2 → 3」：不升，保持 2。**

理由是 P1-5 第一节那个定义：`BackupMedia extends Omit<MediaItem, "blob" | "thumbBlob">`。它是**派生类型**，`MediaItem` 加字段它就自动跟着加，导出路径一行不用改。

而 P1-6 已经在**同一情形下连拒三次**：E1 给 `MediaItem` 加 `thumbMime`、E3 加字段、J1 加 `orphanedAt`，三次的结论都是「不再 +1」。**`formatVersion` 是给结构变更用的，可加可缺且有 `""` 回退的新字段不算结构变更**。

真升到 3 的代价是实的：导入分支从「`v1` / `v2`」变成三支，而三支的行为完全一样，**白白多一个永久要兼容的版本号**。

</aside>

所以本步**只改导入**。旧备份（任何 v1 / v2 文件）里这两个字段是 `undefined`，而类型上已经是必填，必须在落库前补齐。

<aside>
🛑

**J2  作废上一版的那两段补丁（它写错了位置）。**

上一版把 `remoteUrl` / `thumbRemoteUrl` 的兜底写在事务里的 `db.media.put({ ...rest, blob, thumbBlob, ... })`。**那个作用域里根本没有 `rest` / `blob` / `thumbBlob` 这三个变量**——它们是事务**外**那个解码循环的局部变量，拉进来就是三条 `TS2304 Cannot find name`。

**正确位置：兜底要在“造 `decoded`”的那个循环里做**（`rest` 唯一存在的地方），事务里回到最简的 `await db.media.put(m)`。这也更安全：`decoded` 的类型是 `MediaItem[]`，字段补在那里才会被编译器盯住，补在 `put()` 里则是“只要形状对了就放行”。

</aside>

四处改动，全部已合进下面的整文件（第十三节 K1 的写页规矩：代码只在唯一一份整文件块里维护）：

| # | 位置 | 改动 |
| --- | --- | --- |
| 1 | `importAll` 的 `decoded.push({...})` | 加 `remoteUrl` / `thumbRemoteUrl` 兜底。**唯一正确的地方** |
| 2 | 事务里的 media 循环 | 改回 `await db.media.put(m)`，什么都不拼 |

```tsx
import { LOCAL_MEDIA_PREFIX } from "@/shared/text"
import {
  BACKUP_FORMAT_VERSION,
  checkBackup,
  contentTooNew,
  type BackupFile,
  type BackupMedia,
  type ImportConflict,
} from "@/shared/backup"
import { newId } from "@/shared/ids"
import { normalizeTagName } from "@/shared/tags"
import { utcNow } from "@/shared/time"
import { CONTENT_SCHEMA_VERSION, type Entry, type MediaItem, type Tag } from "@/shared/types"

import { localMediaRepo } from "./mediaRepo"
import { db } from "./schema"

export interface ImportReport {
  entriesAdded: number
  entriesUpdated: number
  entriesSkipped: number
  /** 正文 schemaVersion 比本机新，只能跳过 */
  entriesTooNew: number
  tagsAdded: number
  tagsMerged: number
  mediaAdded: number
  mediaSkipped: number
}

function blobToBase64(blob: Blob): Promise<string> {
  return new Promise((resolve, reject) => {
    const reader = new FileReader()
    reader.onerror = () => {
      reject(reader.error ?? new Error("读取图片失败"))
    }
    reader.onload = () => {
      // readAsDataURL 给的是 "data:image/png;base64,xxxx"，只保留逗号后面那段。
      const s = String(reader.result)
      resolve(s.slice(s.indexOf(",") + 1))
    }
    reader.readAsDataURL(blob)
  })
}

async function base64ToBlob(b64: string, mime: string): Promise<Blob> {
  // 走 fetch 解 data URL，比手写 atob + Uint8Array 少一层出错空间，
  // 也不会在大图上把主线程卡住那么久。
  const res = await fetch(`data:${mime || "application/octet-stream"};base64,${b64}`)
  return res.blob()
}

/**
 * 根据图片文件头识别真实 MIME。
 *
 * 主要用于兼容 v1 备份：v1 没有 thumbMime，
 * 因此缩略图不能简单使用原图的 rest.mime。
 */
function detectImageMime(b64: string, fallback: string): string {
  const raw = atob(b64.slice(0, 32))
  const bytes = Array.from(raw, (char) => char.charCodeAt(0))

  // JPEG
  if (bytes[0] === 0xff && bytes[1] === 0xd8 && bytes[2] === 0xff) {
    return "image/jpeg"
  }
  // PNG
  if (bytes.slice(0, 4).join(",") === "137,80,78,71") {
    return "image/png"
  }
  // GIF
  const head = raw.slice(0, 6)
  if (head === "GIF87a" || head === "GIF89a") {
    return "image/gif"
  }
  // WebP
  if (raw.slice(0, 4) === "RIFF" && raw.slice(8, 12) === "WEBP") {
    return "image/webp"
  }
  return fallback || "application/octet-stream"
}

/** 正文里的图片引用是 local://media/{id}，改 id 就必须同步改正文。 */
function remapMediaRefs(content: Entry["content"], map: Map<string, string>): Entry["content"] {
  if (!content || map.size === 0) {
    return content
  }
  let json = JSON.stringify(content)
  for (const [from, to] of map) {
    json = json.split(`${LOCAL_MEDIA_PREFIX}${from}`).join(`${LOCAL_MEDIA_PREFIX}${to}`)
  }
  return JSON.parse(json) as Entry["content"]
}

export const localBackupRepo = {
  /**
   * 全量导出。
   *
   * media 逐条读、逐条编码，而不是一次 toArray()：
   * 后者会把所有原图同时握在内存里，几百张图直接把标签页搞崩。
   * base64 本身还有 4/3 的膨胀，两处叠加就是灾难。
   *
   * P2-0 之后这里一行不用改：...rest 会自动带上新增的 remoteUrl /
   * thumbRemoteUrl（BackupMedia 是 Omit<MediaItem, "blob" | "thumbBlob"> 的派生），
   * entries 的 serverUpdatedAt 同理。所以 formatVersion 不升（J1）。
   */
  async exportAll(onProgress?: (done: number, total: number) => void): Promise<BackupFile> {
    const [entries, tags, mediaIds] = await Promise.all([
      db.entries.toArray(),
      db.tags.toArray(),
      db.media.orderBy("id").primaryKeys(),
    ])

    const media: BackupMedia[] = []
    for (let i = 0; i < mediaIds.length; i++) {
      const m = await db.media.get(mediaIds[i] as string)
      if (!m) {
        continue
      }
      const { blob, thumbBlob, ...rest } = m
      media.push({
        ...rest,
        // 原图
        blobBase64: await blobToBase64(blob),
        // 缩略图。同时保存 thumbMime，避免导入时错误使用原图 MIME。
        thumbBase64: thumbBlob ? await blobToBase64(thumbBlob) : null,
        thumbMime: thumbBlob?.type || null,
      })
      onProgress?.(i + 1, mediaIds.length)
    }

    return {
      app: "quire",
      formatVersion: BACKUP_FORMAT_VERSION,
      exportedAt: utcNow(),
      contentSchemaVersion: CONTENT_SCHEMA_VERSION,
      counts: {
        entries: entries.length,
        tags: tags.length,
        media: media.length,
      },
      entries,
      tags,
      media,
    }
  },

  /** 导入。raw 是 JSON.parse 之后的结果，校验在里面做。 */
  async importAll(raw: unknown, conflict: ImportConflict = "preferNewer"): Promise<ImportReport> {
    const checked = checkBackup(raw)
    if (!checked.ok) {
      throw new Error(checked.reason)
    }
    const file = checked.file
    const now = utcNow()

    const report: ImportReport = {
      entriesAdded: 0,
      entriesUpdated: 0,
      entriesSkipped: 0,
      entriesTooNew: 0,
      tagsAdded: 0,
      tagsMerged: 0,
      mediaAdded: 0,
      mediaSkipped: 0,
    }

    // ──────────────────────────────────────────
    // 第一段：事务外。先建立 Entry ID 映射。
    //
    // asCopy 时 Entry 和 Media 必须用同一份 entryIdMap，否则
    //   Entry -> 新 ID，Media -> 原 Entry ID
    // 复制出来的图片会仍然挂在原条目上。
    // ──────────────────────────────────────────
    const entryIdMap = new Map<string, string>()
    for (const entry of file.entries) {
      entryIdMap.set(entry.id, conflict === "asCopy" ? newId() : entry.id)
    }

    // ──────────────────────────────────────────
    // Media ID 映射。asCopy 时图片也必须生成新 id，
    // 同时正文中的 local://media/{id} 要同步替换。
    // ──────────────────────────────────────────
    const mediaIdMap = new Map<string, string>()
    const decoded: MediaItem[] = []

    for (const bm of file.media) {
      const { blobBase64, thumbBase64, thumbMime, ...rest } = bm
      const id = conflict === "asCopy" ? newId() : rest.id
      if (id !== rest.id) {
        mediaIdMap.set(rest.id, id)
      }

      // 原图 MIME 直接用备份里的 mime。
      const blob = await base64ToBlob(blobBase64, rest.mime)

      // 缩略图：新版本优先用 thumbMime；v1 没有它，按文件头识别，
      // 不能直接用 rest.mime。
      const thumbBlob = thumbBase64
        ? await base64ToBlob(
            thumbBase64,
            thumbMime || detectImageMime(thumbBase64, rest.mime),
          )
        : null

      decoded.push({
        ...rest,
        id,
        blob,
        thumbBlob,
        dirty: 1,
        // asCopy 时必须用和 Entry 相同的 entryIdMap，否则
        // 新 Entry -> newEntryId、新 Media -> oldEntryId，
        // 图片仍然挂在原条目上。
        entryId: rest.entryId ? (entryIdMap.get(rest.entryId) ?? rest.entryId) : "",

        // ── P2-0 改动 1/4 ──────────────────────────────────────────────
        // v1 / v2 旧备份没有这两个字段，在这里补空串。不能留 undefined：
        // remoteUrl 在 Dexie version 2 里是索引，undefined 会让整行不进索引，
        // 于是「找出未上云的图」那个查询永远看不见它（铁律 4）。
        //
        // 补在这里而不是事务里的 put()：一是 rest 只在本循环里存在，
        // 二是 decoded 的类型是 MediaItem[]，漏字段会当场编译不过。
        //
        // 导入旧备份后这两个空串的含义是「这张图得重新上传一次」，
        // 下一轮 dirty 上行时会自己补回来——正是想要的语义。
        remoteUrl: rest.remoteUrl ?? "",
        thumbRemoteUrl: rest.thumbRemoteUrl ?? "",
      })
    }

    // ──────────────────────────────────────────
    // 标签按 name 归并，不按 id。
    // 同一个「旅行」标签在两台设备上各自新建过，
    // 按 id 导入就会出现两个同名标签。
    // ──────────────────────────────────────────
    const localTags = await db.tags.toArray()
    const tagByName = new Map(localTags.map((t) => [normalizeTagName(t.name), t.id]))

    const tagIdMap = new Map<string, string>()
    const tagsToAdd: Tag[] = []

    for (const t of file.tags) {
      const key = normalizeTagName(t.name)
      const exist = tagByName.get(key)
      if (exist) {
        if (exist !== t.id) {
          tagIdMap.set(t.id, exist)
        }
        report.tagsMerged += 1
        continue
      }
      const id = conflict === "asCopy" ? newId() : t.id
      if (id !== t.id) {
        tagIdMap.set(t.id, id)
      }
      tagByName.set(key, id)
      tagsToAdd.push({ ...t, id, dirty: 1 })
    }

    // ──────────────────────────────────────────
    // 构造最终 Entry。id 必须从 entryIdMap 取，
    // 不能在这里再 newId()，否则 Media 用的 entryIdMap 又失效。
    // ──────────────────────────────────────────
    const incoming: Entry[] = []
    for (const e of file.entries) {
      if (contentTooNew(e, CONTENT_SCHEMA_VERSION)) {
        report.entriesTooNew += 1
        continue
      }
      incoming.push({
        ...e,
        // asCopy 时用预先建立好的 Entry ID。
        id: entryIdMap.get(e.id) ?? e.id,
        // 正文中的 local://media/{oldId} 同步改成新的 media id。
        content: remapMediaRefs(e.content, mediaIdMap),
        // 标签 ID 用归并后的 ID；多个同名来源标签可能映射到同一 ID，必须去重。
        tagIds: [...new Set((e.tagIds ?? []).map((t) => tagIdMap.get(t) ?? t))],
        clientUpdatedAt: e.clientUpdatedAt ?? e.updatedAt ?? now,

        // ── P2-0 改动 3/4 ──────────────────────────────────────────────
        // 旧备份没有这个字段，补空串。
        //
        // asCopy 必须硬置 ""：副本是一个全新的 id，服务端压根不知道它。
        // 把原条的 serverUpdatedAt 拄过来，之后排查时会看到一个从未同步过
        // 的行冒出一个服务端时间戳，直接把人带错方向。
        //
        // 它不参与任何仲裁（仲裁只看 clientUpdatedAt），所以这里怎么填
        // 都不影响同步正确性，只影响可读性。
        serverUpdatedAt: conflict === "asCopy" ? "" : (e.serverUpdatedAt ?? ""),

        dirty: 1,
      })
    }

    // ──────────────────────────────────────────
    // 第二段：纯 Dexie 事务。里面一个非 Dexie 的 await 都不能有。
    // ──────────────────────────────────────────
    await db.transaction("rw", db.entries, db.tags, db.media, async () => {
      // ── Tags ──
      for (const t of tagsToAdd) {
        await db.tags.put(t)
        report.tagsAdded += 1
      }

      // ── Media ──
      for (const m of decoded) {
        // 图片是内容寻址式的死数据，改不了也不会冲突：同 id 就是同一张。
        if (await db.media.get(m.id)) {
          report.mediaSkipped += 1
          continue
        }
        // ── P2-0 改动 2/4 ────────────────────────────────────────────
        // m 已经是事务外造好的完整 MediaItem（含 entryId 映射、
        // remoteUrl / thumbRemoteUrl 兜底）。这里什么都不要拼：
        // rest / blob / thumbBlob 那三个变量不在本作用域，拉进来就是 TS2304。
        await db.media.put(m)
        report.mediaAdded += 1
      }

      // ── Entries ──
      for (const e of incoming) {
        const cur = await db.entries.get(e.id)
        if (!cur) {
          // 改动 4/4：不动。e 已经是造好的 Entry，含 serverUpdatedAt。
          await db.entries.put(e)
          report.entriesAdded += 1
          continue
        }
        if (conflict === "keepLocal") {
          report.entriesSkipped += 1
          continue
        }
        // preferNewer：只有备份更新才覆盖。相等时不动，避免把 updatedAt 白刷一遍。
        if (e.clientUpdatedAt > cur.clientUpdatedAt) {
          await db.entries.put(e)
          report.entriesUpdated += 1
        } else {
          report.entriesSkipped += 1
        }
      }
    })

    // ──────────────────────────────────────────
    // 第三段：事务外对账。必须在 Dexie transaction 结束之后。
    //
    // reconcileAll 会按最终落库的 Entry JSON 校正 media.entryId / sortOrder，
    // 这样导入完成后立刻执行彻底删除，也不会因为旧的 media.entryId 关联
    // 而误删原条目或副本条目的图片。
    // ──────────────────────────────────────────
    await localMediaRepo.reconcileAll()

    return report
  },
}
```

**导入旧备份后不要把这两个字段当真**：`remoteUrl` 补成空串意思是「这张图得重新上传一次」，正是想要的语义；它会在下一轮 `dirty` 上行时自己补回来。
