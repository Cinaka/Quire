# P0 / P1 开发清单（MySQL 8.0 版）

<aside>
🗄️

数据库由 PostgreSQL 调整为 **MySQL 8.0**。受影响的点：`JSONB → JSON`、全文检索需 `ngram` 分词器、`UUID` 用 `BINARY(16)` 或 `CHAR(36)`、字符集统一 `utf8mb4/utf8mb4_0900_ai_ci`。详见「MySQL 8.0 适配要点」。

</aside>

## 一、MySQL 8.0 适配要点（先看这个）

| 原方案（PG） | MySQL 8.0 做法 | 说明 |
| --- | --- | --- |
| `JSONB` | `JSON` | MySQL 8 原生 JSON，支持 `JSON_EXTRACT` / `->>`，但**不能直接建索引** |
| JSON 字段索引 | 生成列 + 索引 | `ALTER TABLE t ADD col VARCHAR(64) GENERATED ALWAYS AS (data->>'$.k') STORED, ADD INDEX(col)` |
| 全文检索 `tsvector` | `FULLTEXT`  • `WITH PARSER ngram` | 中文必须用 ngram，`my.cnf` 里设 `ngram_token_size=2` |
| `UUID PK` | `BINARY(16)`（推荐）或 `CHAR(36)` | 本项目用 **UUID v7**，时间戳已在前 48 bit，**直接存 `uuid.bytes` 原始字节**；**不要**做 v1 的时间位交换（即等价于 `UUID_TO_BIN(x, 0)`） |
| `ENUM` | `ENUM` 或 `TINYINT`  • 应用层枚举 | 推荐 `TINYINT`，改值不用 DDL |
| `TIMESTAMPTZ` | `DATETIME(3)` 存 UTC | MySQL 的 `TIMESTAMP` 有 2038 问题，统一存 UTC 由应用转时区 |
| 部分索引 / `WHERE deleted_at IS NULL` 唯一 | 生成列技巧 | 软删除下的唯一约束需用 `is_deleted` 生成列参与唯一键 |
| 驱动 | `asyncmy`（推荐）或 `aiomysql` | SQLAlchemy 2.0 异步：`mysql+asyncmy://` |

<aside>
⚠️

字符集务必建库时就指定 `CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci`，否则 emoji（心情字段）会写入失败。

</aside>

## 四、P1 涉及的 MySQL 建表语句（P0 阶段先建好）

<aside>
💡

P1 数据只落本地 IndexedDB，但表结构在 P0 就建好，P2 同步时直接用，避免返工。

</aside>

```sql
CREATE DATABASE quire DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

CREATE TABLE users (
  id            BINARY(16)   NOT NULL PRIMARY KEY,
  phone         VARCHAR(20)  NULL,
  email         VARCHAR(128) NULL,
  password_hash VARCHAR(255) NULL,
  nickname      VARCHAR(64)  NULL,
  avatar        VARCHAR(512) NULL,
  timezone      VARCHAR(64)  NOT NULL DEFAULT 'Asia/Shanghai',
  created_at    DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at    DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  UNIQUE KEY uk_phone (phone),
  UNIQUE KEY uk_email (email)
) ENGINE=InnoDB;

CREATE TABLE diary_entries (
  id                BINARY(16)  NOT NULL PRIMARY KEY,
  user_id           BINARY(16)  NOT NULL,
  entry_date        DATE        NOT NULL,
  sort_order        INT         NOT NULL DEFAULT 0,
  title             VARCHAR(255) NULL,
  content           JSON        NULL,          -- Tiptap JSON
  content_text      MEDIUMTEXT  NULL,          -- 纯文本，供全文检索
  mood              VARCHAR(16) NULL,
  weather           VARCHAR(16) NULL,
  from_schedule_id  BINARY(16)  NULL,          -- 幂等关键
  client_updated_at DATETIME(3) NULL,
  created_at        DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at        DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  deleted_at        DATETIME(3) NULL,
  UNIQUE KEY uk_from_schedule (from_schedule_id),
  KEY idx_user_date (user_id, entry_date DESC),
  KEY idx_user_updated (user_id, updated_at),
  FULLTEXT KEY ft_content (title, content_text) WITH PARSER ngram
) ENGINE=InnoDB;

CREATE TABLE tags (
  id         BINARY(16)  NOT NULL PRIMARY KEY,
  user_id    BINARY(16)  NOT NULL,
  name       VARCHAR(32) NOT NULL,
  color      VARCHAR(16) NULL,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  UNIQUE KEY uk_user_name (user_id, name)
) ENGINE=InnoDB;

CREATE TABLE entry_tags (
  entry_id BINARY(16) NOT NULL,
  tag_id   BINARY(16) NOT NULL,
  PRIMARY KEY (entry_id, tag_id),
  KEY idx_tag (tag_id)
) ENGINE=InnoDB;

CREATE TABLE media (
  id         BINARY(16)   NOT NULL PRIMARY KEY,
  user_id    BINARY(16)   NOT NULL,
  entry_id   BINARY(16)   NULL,
  url        VARCHAR(512) NOT NULL,
  thumb_url  VARCHAR(512) NULL,
  width      INT NULL,
  height     INT NULL,
  size       BIGINT NULL,
  sort_order INT NOT NULL DEFAULT 0,
  created_at DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  KEY idx_entry (entry_id)
) ENGINE=InnoDB;
```

## 五、风险与注意事项

1. **Repository 抽象一定要在 P1 做**。如果 P1 直接在组件里写 `db.entries.add()`，P2 接云端时要改几十处，成本翻倍。
2. **UUID v7 而非 v4**。v7 的前 48 bit 就是毫秒时间戳且为大端序，**原始字节天然单调递增**，写入 InnoDB 聚簇索引接近顺序写；v4 会导致严重页分裂。**切记不要对 v7 做 `UUID_TO_BIN(x, 1)` 的时间位交换**——那是为 v1 设计的，用在 v7 上会把低位字节挑到最前面，反而彻底破坏顺序性。
3. **IndexedDB Blob 内存泄漏**。列表页大量 `createObjectURL` 不释放会让移动端浏览器崩溃，务必在组件卸载时 revoke。
4. **ngram_token_size 改了要重建索引**。这个参数只能在 `my.cnf` 设置且需重启，改完已有 FULLTEXT 索引要 `OPTIMIZE TABLE` 重建，P0 阶段就定好。
5. **软删除下的唯一约束**。`tags` 表若要支持删除后重建同名标签，需把 `deleted_at` 转成生成列参与唯一键，否则会撞唯一约束。
6. **Tiptap JSON 结构要版本化**。`content` JSON 里存一个 `schemaVersion`，未来改编辑器时好做数据迁移。
7. **P1 不要碰登录**。一旦开始做账号，游客态的边界会被打破，容易返工。严格守住「P1 只做本地」。
8. **不用 Docker 后的唯一风险点**是环境参数靠人工保证。`ngram_token_size` 配错时**不报错**，只是中文搜不到，排查成本极高。已在第六节附上部署参数核对清单，上线前跑一次 SQL 即可。

## 七、多端差异化架构约定

### 1. 实际是三个平台，不是两个

| 平台 | 定位 | 代码关系 |
| --- | --- | --- |
| PC 浏览器 | 核心场景：日记本视图、打印、导出 | 与手机浏览器**同一套代码**（响应式） |
| 手机浏览器 / PWA | 随手记录 | 同上 |
| 微信小程序（二期） | 引流与轻量场景 | **不复用 UI**，只复用逻辑 |

小程序不能调起打印机、无 DOM（Tiptap 无法运行）、PDF 导出受限、自定义字体受限——三个核心卖点全废，因此**共用的是逻辑，不是界面**。

```jsx
┌────────────────────────────────────┐
│  shared  ← 纯 TS，零 UI，零平台 API             │
│  · 农历宜忌封装     · 日期分支判定规则        │
│  · 类型定义         · 内容格式转换           │
│  · API 契约类型     · 连续天数 / 校验规则      │
└──────┬──────────────────────────┬────────┘
       │                              │
┌──────┴────────────┐   ┌────────┴─────────┐
│ frontend（Vue3）     │   │ 小程序（二期）       │
│ PC + 移动浏览器     │   │ 只做签到 + 速记 +   │
│ 全功能响应式       │   │ 浏览，做减法         │
└──────────────────┘   └─────────────────┘
```

### 2. PC 与移动的差异处理：三级递进

**能用第 1 级就绝不用第 3 级。**

| 级别 | 手法 | 覆盖比例 | 说明 |
| --- | --- | --- | --- |
| 第 1 级 | 纯 CSS 断点（Tailwind `md:`） | ~80% | 布局、栏数、间距、TabBar / 侧边栏互斥 |
| 第 2 级 | 逻辑与呈现分离 | ~15% | 结构差异大时，拆 `XxxDesktop.vue` / `XxxMobile.vue`，共用同一个 composable |
| 第 3 级 | 平台能力适配层 | ~5% | 打印、下载、字体加载、剪贴板，全部收进 `capabilities/` |

**禁止事项**：不要在单个组件里用 `v-if` 并列两套完整模板；不要在业务组件里直接调 `window.print()` 或 `document.createElement`。

第 2 级的正确形状：

```tsx
// composables/useHome.ts —— 逻辑唯一来源，两端共用
export function useHome() {
  const date = ref(dayjs())
  const lunar = computed(() => getLunarInfo(date.value)) // 来自 shared
  const entries = ref<Entry[]>([])
  async function load() {
    entries.value = await entryRepo.listByDate(date.value.format("YYYY-MM-DD"))
  }
  return { date, lunar, entries, load }
}
```

```
<!-- views/HomeView.vue —— 只做分发，不含业务逻辑 -->
<script setup lang="ts">
import { defineAsyncComponent } from "vue"
import { useBreakpoint } from "@/composables/useBreakpoint"
const { isDesktop } = useBreakpoint()
const Desktop = defineAsyncComponent(() => import("./home/HomeDesktop.vue"))
const Mobile = defineAsyncComponent(() => import("./home/HomeMobile.vue"))
</script>

<template>
  <component :is="isDesktop ? Desktop : Mobile" />
</template>
```

第 3 级的能力适配层：

```tsx
// capabilities/index.ts
export interface Capabilities {
  canPrint: boolean
  canExportPdf: boolean
  print(): Promise<void>
  saveFile(blob: Blob, filename: string): Promise<void>
}
```

业务代码只写 `if (caps.canPrint)`，UI 自动降级（按钮置灰或隐藏）。将来上小程序只需提供一份 `mpCapabilities` 实现，业务层零改动。

### 3. 路由差异

移动端「列表 → 详情」是两个页面，PC 上应为同屏双栏。保持路由结构一致（保证链接可分享），在 PC 上把 `/entry/:id` 作为 `/list` 的子路由渲染到右栏即可。

### 4. 内容存储格式（现在必须定下来）

<aside>
🔑

这是唯一一个「现在不想清楚，将来必然返工」的点。

</aside>

| 方案 | PC 体验 | 小程序可行性 | 结论 |
| --- | --- | --- | --- |
| Tiptap JSON | ⭐⭐⭐⭐⭐ | 需自写 JSON → 小程序节点渲染器（2–3 天） | ✅ **采用** |
| Markdown | ⭐⭐⭐⭐ | `towxml` 直接渲染，几乎零成本 | 备选 |
| HTML 字符串 | ⭐⭐⭐ | `rich-text` 标签白名单坑多 | ❌ |

采用 Tiptap JSON，但**从第一天起就在 `shared` 里写好三个纯函数**，把格式转换与平台彻底解耦：

```tsx
// shared/content.ts
export function toPlainText(doc: TiptapDoc): string  // 存 content_text，供全文检索与列表摘要
export function toMarkdown(doc: TiptapDoc): string   // 供导出、小程序渲染
export function fromMarkdown(md: string): TiptapDoc  // 供导入、小程序速记回写
```

小程序端的功能边界：**只读渲染走 Markdown，编辑只支持纯文本速记**（回写时 `fromMarkdown`）。这个边界诚实且足够——用户在小程序里本来也不会写长文。

### 5. P1 阶段需要留的三个口子

**不要为了将来的小程序现在上 uni-app，也不要现在建 monorepo 分包。**只需在 P1 留好三个口子，成本几乎为零；等 P5、P6 做完再补，成本是重写。

- [x]  **`src/shared/`** 目录（将来平移为独立包）：农历封装、日期分支判定、内容格式转换、类型定义。**里面禁止出现 `window`、`document`、Vue API** —— 已立（`types / ids / time / text / backup / bytes`），每轮验收都跟一遍 grep
- [x]  **`src/capabilities/`** 能力适配层：打印、下载、字体加载全走这里 —— P1-5 落下第一个成员 `download.ts`（`saveBlob`），视图层不再碰 `document`
- [ ]  **`useXxx()` composable 承载业务逻辑**，组件只管呈现（与 P1-1 的 Repository 抽象同一思路：让平台相关的东西可替换）

## 八、时区与日期语义约定

<aside>
🕒

**项目里有两类完全不同的时间，不能混。**

一类是**瞬间**（这条记录什么时候写的），一类是**日历日**（这篇日记算哪一天）。前者有时区，后者没有。

混用的后果很隘手：它**不报错**，只在本地凌晨 0–8 点这个窗口里出错。白天写代码、白天测试，永远碰不到。

</aside>

### 1. 两类字段的语义分工

| 字段 | 类型 | 语义 | 值由谁决定 |
| --- | --- | --- | --- |
| `created_at` / `updated_at` / `client_updated_at` / `deleted_at` | `DATETIME(3)` | **UTC 瞬间**。回答「什么时候发生的」 | 服务端（`client_updated_at` 由客户端写，也是 UTC） |
| `entry_date` | `DATE` | **日历日，无时区**。回答「这篇算哪一天的」 | **客户端**按本地时区算好传入 |

`entry_date` 是用户的主观归属，不是系统事实。补记上周三的日记，`entry_date` 是上周三，`created_at` 是今天——这两个值就是该对不上的。

### 2. 三条规范

1. **所有 `DATETIME(3)` 存 UTC。** 后端写入统一走 `utcnow()`，**禁用 `datetime.now()`**。
2. **`entry_date` 客户端算好，服务端原样存。** 服务端**不得对它做任何时区换算**。
3. **只在展示层转本地**：`dayjs.utc(x).local().format(...)`。存储层、传输层、比较运算全部用 UTC。

### 3. 禁用 `toISOString().slice(0, 10)`

这是本项目最容易踩的一个坑。它取的是 **UTC 日期**，不是本地日期：

```
上海时间  2026-08-19 00:30  （用户心里：19 日凌晨写的）
对应 UTC   2026-08-18 16:30
.slice()  → "2026-08-18"   ❌ 日记被归到了前一天
```

上海是 UTC+8，所以只有本地 **0:00–8:00** 这八个小时会错，其余时间结果恰好相同。而凌晨写日记恰恰是高频场景。

**统一用 `todayLocal()`**（定义在 `src/shared/time.ts`，见 P1-1 源码页）。项目里任何地方需要「今天是哪天」，只能调它。

### 4. MySQL 侧为什么必须设 `default-time-zone = '+00:00'`

不设的后果不是连不上，而是**同一列里混进两种时间**：

- 应用层 `utcnow()` 写入的是 UTC
- 但建表时的 `DEFAULT CURRENT_TIMESTAMP(3)` 与 `ON UPDATE` 是由 **MySQL 自己**求值的，用的是会话时区
- 服务器时区是 `system`（即 CST）时，这两条路径差 **8 小时**，而数据库**不会报任何错**

现象是“排序偶尔不对”“刷新时间比创建时间早 8 小时”这类很难归因的问题。参数只能写配置文件（本项目写在 `/etc/mysql/mysql.conf.d/zz-quire.cnf`）并重启，**且必须用偏移量而非地区名**——写 `'Asia/Shanghai'` 在未导入时区表的新装实例上会直接启动失败。

### 5. `users.timezone` 字段是干什么的

它**不参与存储**（存储永远是 UTC），也不是给展示用的（浏览器自己知道本地时区）。存 IANA 名称如 `Asia/Shanghai`，**P1 阶段完全用不到**。

它的真正用途从 P2 开始，只有两个：

1. **服务端定时任务需要知道“该用户的当地几点”**。签到提醒、日程到期那些任务跑在服务器上，服务器看不到浏览器。要在用户当地时间早上 8 点推送，就必须知道他在哪个时区。
2. **连续天数的归属判定**。“连续签到”要定义“一天”的边界，跨时区旅行时必须有一个基准时区，否则一次东西向飞行就能把连续记录给弄断或刷双。

### 6. 核对清单

- [ ]  后端全局搜不到 `datetime.now()`：`grep -rn "datetime.now()" app/`
- [ ]  前端全局搜不到 `toISOString().slice`：`grep -rn "toISOString().slice" src/`
- [ ]  `SELECT @@global.time_zone;` 返回 `+00:00`（**不是 `system`**）
- [ ]  `SELECT TIMEDIFF(NOW(), UTC_TIMESTAMP());` 返回 `00:00:00`
- [ ]  把本机时间改到凌晨 1 点写一篇日记，确认 `entryDate` 是当天而非前一天
