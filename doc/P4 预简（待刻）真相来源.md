## 三、已确认的日期、生命周期与内容语义

1. `remindDate` 和 `entryDate` 均为 `YYYY-MM-DD` 自然日，服务端保存 DATE 不做时区换算；created/updated/clientUpdated/deleted/convertedAt 是 UTC。
2. 首版到期判定：`pending && 未删除 && remindDate <= todayLocal()`，到期是派生状态，不每过一天写 dirty。未来分流也使用同一个日期函数。
3. 该选择与 P1 日记本地日期一致。不同设备时区在午夜可能对“今天/到期”显示不同；日期字段本身不漂移，转简身份不受时区影响。不承诺跨时区瞬时一致到期。
4. P3 仍由 `users.timezone` 定义签到日，绝不借预简的设备日期改写签到。若用户要求账号时区统一到期，必须改本节和离线日期算法后再批准，不与本地语义混搭。
5. 生命周期 `pending → converted`；converted 终态。删除是 deletedAt/isDeleted 正交标志。已转简不可重新转简、改源内容或撤销转换；查看跳到关联日记。
6. 原日记移入断简/恢复不改变已转简事实；永久弃去也不解锁源日程再生成。
7. pending 到期/逾期可继续编辑、改期。转简复制一个明确修订的内容快照，之后修改日记不反向同步源预简。
8. 新建日期分流在首个自动保存、草稿恢复和 route query 使用之前完成。日记与日程草稿分别命名，旧日记草稿继续可恢复；不复用同一个 meta 键相互覆盖。

### 2. Dexie v3

在现有 v1/v2 后新增 version(3)，**不改旧版本定义，不重建/清空现有表**。

Schedule 建议字段：`id`（UUID v7）、`remindDate`、`title`、`content`、`contentText`（repo 从 content 同次派生）、`status`（pending/converted）、`convertedEntryId`（null 或稳定来源 ID）、`convertedAt`、`createdAt`、`updatedAt`、`clientUpdatedAt`、`serverUpdatedAt`（未同步为空串）、`deletedAt`、`isDeleted`（0/1）、`dirty`（0/1）。

日程独立游标、错误、冲突、离线转简意图使用独立 meta 键（例如 scheduleLastSyncAt/scheduleConflicts/scheduleSyncErrors/scheduleConversions）；不覆盖 lastSyncAt/conflicts/pendingPurges。离线转简事务包含 entries/schedules/meta，失败全部回滚。已写库数据一律不得因网络失败删除。

- 新客户端读取 v1/v2：缺 schedules/转换意图视为空；不制造历史未来日记迁移。

### 1. 数据库

converted 源关系作为长期幂等记录保留：P4 不启用日程墓碑定时清理；不能套用 P2 180 天清理后忘记转换事实。P2 对日记墓碑清理不因此改语义。

### 2. API 契约

统一 `/api/v1`、Envelope `{code,message,data}`、snake_case、P2 JWT/refresh、账号所有权检查。路径以独立日程命名空间承载，不复用 P3 checkins。

| 方法 | 拟路径 | 契约 |
| --- | --- | --- |
| GET | `/schedules` | 日期/状态/已删除筛选，分页 items/total/page/page_size |
| GET | `/schedules/{id}` | 当前账号单条，跨账号统一不可见 |
| PUT | `/schedules/{id}` | 客户端 UUID 幂等 upsert；只允许 pending 编辑；删除/恢复也走修订写入 |
| POST | `/schedules/sync/push` | 每批最多 50，逐项 applied/stale/error，不让单条阻断正常日记同步 |
| GET | `/schedules/sync/changes` | 独立 since/after_id/until/limit；updated_at/id 排序、固定快照高水位、含墓碑 |
| POST | `/schedules/{id}/convert` | 持久化来源幂等转换，服务端事务更新日程与日记，重复返回既存关联 |

静态 /sync 路由注册先于 /{id}，避免误当 UUID。非法 UUID/日期/状态为 422，鉴权失败 401，不可见 404，修订/终态竞争 409 并提供当前版本；唯一键竞争不得泄露 SQL 或变成 500。

PUT 不接受用户伪造 converted 状态。convert body 建议包含目标 entry_date、expected_schedule_client_updated_at，以及离线创建的日记快照/其 client_updated_at；不能接受任意不同来源的 entry id。返回包含 schedule、关联 entry、created 与明确冲突信息。服务端不把设备“今天”当防刷权威：日程日期是主观日历日，转换 UI 限制未来，后端验证结构、版本、所有权和关系；若要求服务端账号日强校验，需先改第三节统一日期口径。

## 六、已确认的离线转简与跨设备幂等

### 1. 为什么现有 from_schedule_id 唯一键还不够

现有 entries upsert 不处理“两个不同 Entry ID 指向同一来源”的唯一键竞争；只加按钮会出现 MySQL 冲突/重试失败。本地 EntryCreate 的普通新 UUID 也不能保证双设备同源只生一篇。

推荐**稳定映射：转换日记 `entry.id = schedule.id`，`fromScheduleId = schedule.id`**。两个资源表分离，因此保留 UUID v7 格式、不需引入 UUID v5/hash 或新依赖；这是本轮设计建议，不是历史实现。转换前若同 ID 日记已存在但来源不同，返回冲突，不覆盖。保留服务端 `uk_from_schedule` 作为第二层约束。

### 2. 本地与服务端提交分开标识

- 游客/离线：本地事务创建稳定 ID Entry、标记 Schedule converted、写持久化转换意图；显示「已在本机转简，待同步」，不说“云端成功”。
- 已转简打开同一条记录；多标签页必须在事务内重读状态，以稳定主键和来源校验避免重复。
- 登录同步先 push 日程到确认版本，再处理转换意图。服务端锁定来源，比较 expected revision，在**同一数据库事务**里创建/读取关联 Entry 并终态化来源；同时请求以唯一键/重读返回同一 ID。
- 服务端已转换时不再次 upsert 原预简快照覆盖已编辑日记；返回关联关系及当前版本。失败或超时保留意图，下一次幂等重试恢复。
- 转简期间本地又编辑日记：成功响应只确认发送时的修订，不清掉新修订 dirty。之后回到正常 P2 日记同步。
- 另设备离线转换但内容不同：稳定 ID避免多篇，**不保证内容自动合并**；先保留本地快照和服务端版本供取舍，不让返回结果无声覆盖用户的新文字。
- pending 改期/编辑/删除与转换竞争：服务端版本+行锁决定先后。修订不匹配返回冲突；删除先成功则转换失败并保留本地候选；转换先成功则 pending 修改被拒并保留冲突，不允许状态退回 pending。
- 已关联 Entry 软删除、永久弃去、服务端 180 天清理后仍不再生成；converted source 保留关系，返回「关联日记已删除/已弃去」，不把不存在当首次转换。

### 3. 对 P2 的最小但真实影响

推荐独立日程 push/changes，不改变原 P2 wire payload 或 lastSyncAt 的含义；独立游标可完整拉取而不丢“没有日记更新的日程”。共用前台/online/debounce/retry调度，但日程失败不能卡住普通日记/媒体。

**无法承诺 P2 源码零改动**：未确认的转换 Entry 不能先被普通 P2 push 当日记提交、也不能被普通 pull 吞掉。必须在 P2 候选/应用入口加入窄范围“未确认转换集合”保护：这些来源 Entry 留待专用 convert 提交和冲突处理，普通 Entry 仍按原 P2 流程。转换队列与日程同步 single-flight、账号 generation 和持久化恢复都必须有测试。

不得把推送响应缺失 schedules 当成功；新前端遇旧后端 404/能力不支持时保留所有本地日程和转换意图，暂停 P4 云端处理并清楚提示，普通 P2 继续运行，不清 dirty、不跳游标。恢复部署后可重新同步。

P2 文档的“dirty 永不直接覆盖”与当前 pullAll 的实际行为存在细节差异（严格更新的服务端版本会先留档再写入）。本轮不借此重构冻结的 P2；P4 自己明确：未确认日程编辑/转换先留冲突，未经取舍不直接覆盖。普通日记回归按当前 main 基线，不声称旧实现不存在的保证。

### 数据形状与操作契约

- 使用既定meta.scheduleDraft，原meta.draft及draftRepo源码保持不变。journal自身formatVersion=1，含递增revision与draft/null；这与JSON备份formatVersion=3是不同版本轴，不新增meta键或Dexie版本。
- 草稿含独立draftId、scheduleId/null、baseClientUpdatedAt/null、remindDate、title、文本型EntryContent/null及updatedAt。空标题/正文和已到期日期可以保留为安全草稿；保存草稿不创建Schedule/Entry、不写dirty、不发网络，也不改变新建业务记录的未来日期校验。
- read返回owner/ownerGeneration/revision操作租约及empty/recoverable/alreadySaved/conflict/sourceUnavailable判断。来源删除/转换/缺失/不支持正文版本时保留用户文字；read不自动清空，即使正文已相同也须经确认回执或明确弃去。
- save在同一meta/schedules事务复核归属、恢复代际和CAS修订；同一会话需带原draftId。已有不同草稿或不同目标不能覆盖，必须先处理当前槽位。clear保留递增空标记，不delete后归零；旧保存回调不能重新写回。
